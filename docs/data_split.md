# 开发集与测试集划分

本次划分面向 B 组三分类事实核查开发。来源为原始 `benchmark_1011` 数据，
遵循其[数据说明](../data/raw/benchmark_1011/数据说明.md)：按 `group` 整组隔离，
基础能力集与核心挑战集分开评测。

## 来源与保存方式

原有 `benchmark_1011/` 整体迁移到 `data/raw/benchmark_1011/`。
其中两个 JSONL 文件及 `数据说明.md` 保留原文件内容。
原有 `docs/选题.txt`、`docs/AB对抗组选题说明.docx` 迁移到 `docs/references/`。

| 数据集 | 样本数 | 组数 | 机制数 |
| --- | ---: | ---: | ---: |
| 基础能力集 | 900 | 105 | 7 |
| 核心挑战集 | 885 | 143 | 7 |

两个原始 JSONL 的 SHA-256 固定在 `configs/data_split.json` 中。
脚本在划分前验证文件哈希与样本 / 组数量，避免原始文件意外变化后静默重新划分。
`.gitattributes` 对 `data/raw/` 禁用换行转换，以保留原始字节。

## 方法

参数为 `seed=42`、`test_fraction=0.2`、`candidates=512`，算法版本为
`mechanism_group_hash_candidates_v1`。

1. 对每份数据独立处理，确认 ID 唯一、必需字段非空、标签合法且无重复的证据与陈述组合。
2. 将同一 `group` 的所有样本绑定。每个组必须只属于一个 `mechanism`。
3. 在每个机制内部，测试组数取 `组数 × 0.2` 的四舍五入值，至少保留一个开发组和一个测试组。
4. 用种子、数据集名、机制名、候选编号和组 ID 的 SHA-256 排序产生 512 个候选整组划分。
5. 选择样本测试占比及各标签测试占比与 0.2 的平方偏差之和最小的候选；同分时按组 ID 排序打破平局。
6. 输出按 ID 排序的 JSONL、逐样本归属清单和统计报告。

候选选择只使用标签与样本数量来平衡分布，不运行模型、不依据测试分数选择划分。
算法与原始文件行顺序无关；相同数据、参数和代码产生相同字节的输出。
派生 JSONL 的字段排序和行序会规范化，但所有字段值保持原样。

## 检查结果与范围

两份数据及合并后的全局隔离检查均通过：所有原始样本恰好出现一次，字段值未变，
开发与测试之间的 ID、组、证据与陈述组合均无交叉。
每份数据的开发和测试侧均包含全部三类标签和七种机制。

额外检查表明，开发与测试之间完全相同的 `claim`、`evidence` 和 `source_title`
值数量也均为 0，文本比较时仅去掉首尾空白。
这些检查不包含语义近重复识别，也不证明数据未出现在某个模型的预训练语料中。

原始基础能力集的 900 条记录均标记 `human_review_status=pending`，
核心挑战集的 885 条均标记 `adjudicated`。这些是来源字段，保持原样；
此次工作未重新裁决标签，也没有将基础能力集标为已审核。

## 使用与更新

开发读取 `basic/dev.jsonl` 或 `challenge/dev.jsonl`；最终测试读取对应 `test.jsonl`。
模型输入只使用 `claim` 和 `evidence`，`label` 用于监督或评测，
其他字段用于管理和分项统计。不要把完整 JSON 记录直接作为模型提示词。

运行 `python scripts/split_dataset.py --check` 可只读校验原始哈希和所有派生文件。
两个 `manifest.json` 记录逐样本的 ID、组、机制与子集归属，以及输出 JSONL 的哈希。

`v1` 作为当前冻结版本。若确实要更改参数，应保留当前版本，复制配置文件并将
`output_dir` 改为新目录，例如 `data/splits/v2`，再用 `--config` 指定新配置。
已有输出与新结果不同时脚本默认拒绝覆盖；`--overwrite` 仅用于明确需要重建当前版本的情况。
测试集已经用于最终评测后，重新划分不能替代一份真正未使用过的新测试集。
